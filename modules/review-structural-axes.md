## 1. 왜 이 모듈이 있는가

리뷰는 결함(요구사항 불일치·버그·영향범위)을 잘 찾는다. **더 나은 구조**는 못 찾는다.

원인은 능력 부족이 아니라 **묻지 않음**이다. 통제 A/B 실측: 스키마·cap·에이전트·모델을 전부 고정하고 브리프만 결함축 → 구조축으로 바꿨더니 `review-arch` 1콜이

- 대안 명시 **9/10** (기존 3-렌즈 24건은 코드 형태 대안 2/24)
- 삭제 라인 정량 **10/10** (기존 0/24)
- 기존 24건이 못 잡은 **신규 6건**
- 총 삭제 가능 **95줄 ≈ 변경량의 29%** 산출

를 냈다. 즉 하네스가 축을 열어주면 모델이 채운다 (`guides/prompt-optimization.md` §3b H1 — *"하네스 컴포넌트는 모델이 혼자 못하는 것에 대한 가정. 가정이 틀리면 성능 저해"*).

## 2. Lead 주입 절차

⛔ **참조만으로는 실행되지 않는다.** Progressive Disclosure에서 Level 3 파일은 명시 Read가 있어야 로드된다. Lead가 **이 파일을 Read해서 브리프 문자열에 넣는다.**

```
Lead: Read(modules/review-structural-axes.md) → §3 축 + §4 경계 문구를 args로 전달
  peer-review: Workflow({ …, args: { …, structuralContext } })  → arch 프롬프트에만 주입
  fz-review:   Workflow({ …, args: { …, structuralContext } })  → arch 프롬프트에만 주입
```

⛔ **arch 렌즈에만 주입한다.** 이유 둘:
1. **결함 탐지 회귀 방어** — quality/correctness가 결함 축을 그대로 유지해야 한다. 전 렌즈에 주입하면 모두 구조를 보고 버그를 놓친다.
2. **검증 범위 일치** — A/B는 `review-arch` 1개로만 측정됐다. 전 렌즈 주입은 측정 범위를 넘는다.

비용(실측 기준): 축 블록 약 1,140자 → 1콜 주입 시 Tier 2 총량의 **약 0.2%**. 3콜 주입이면 0.6%.

⛔ **§6 craft 축(F~J)의 기본값은 스킬마다 다르다.** fz-peer-review 는 기본으로 §6 을 브리프에 더한다(`craftAxes:false` 로 끈다 — v4.42.0). fz-review 는 `craftAxes:true` 로 부를 때만 더한다(기본 off). 규칙 레코드가 있으면 어느 쪽이든 `projectRulesPath` 도 넘긴다. Lead 가 직접 적용하는 경로도 같다 — Tier 0/1(fz-peer-review)은 기본으로 §6 을 적용하고, fz-review light 는 craft 를 쓰기로 했을 때만 적용한다.

## 3. 축 5개

각 축은 "무엇을 세고, 무엇을 제시하는가"로 끝난다. **"해당 없음"도 유효한 답이지만 왜 없는지를 쓴다** — 그게 축을 살아있게 하는 장치다.

### A. 메서드 책임 밀도

한 메서드가 몇 가지 일을 하는가. **줄 수·중첩 깊이·조기 return 개수를 센다.** 더 작은 단위로 쪼갤 수 있으면 쪼갠 형태를 제시한다.

이유: 책임이 몰린 메서드는 컴파일도 되고 테스트도 통과한다. 세지 않으면 "읽기 어렵다"는 인상으로만 남고 리뷰어가 판단할 근거가 없다.

### B. 구조 대안 ≥2

같은 요구를 만족하는 **다른 구조 2개**를 제시하고 각각 trade-off 1줄. "현행이 최선"이라고 판단하면 **왜 다른 안이 열등한지**를 쓴다.

이유: 대안이 하나면 비교할 축이 없다. 그리고 현행을 옹호하는 근거를 쓰는 과정에서 옹호가 안 되는 경우가 드러난다.

### C. 삭제 > 추가

추가 라인을 줄이거나 기존 코드를 없앨 수 있는 재구성이 있는가. **있으면 몇 줄이 사라지는지 센다.**

이유: 같은 동작을 더 적은 코드로 표현하는 것이 진짜 최소 변경이다. 줄 수를 세면 제안의 크기가 리뷰어에게 즉시 보인다.

### D. 구조 결정 3축

세 축 각각에 대안 ≥2 + trade-off 1줄. **템플릿·형제 미러링이라도 "이미 결정됨"으로 넘기지 않는다.**

| 축 | 질문 |
|---|---|
| DI 출처 | 의존성을 내부에서 생성하는가 상위에서 주입받는가. 목(mock) 주입 경로가 있는가 |
| 스레드 가정 | 프레임워크가 보장하는가, 코드가 가정하는가. 소스로 확인했는가 |
| public API 모양 | Bool 플래그/모드 파라미터인가 의도별 분리 함수인가 |

이유: 이 셋은 컴파일러가 검증하지 않고 테스트도 잘 안 걸린다. 그래서 결정이 암묵적으로 굳는다.

### E. 코드 형태

컬렉션 변형(loop vs map/filter)·중첩 인덱스 서브스크립트·반복되는 클로저 보일러플레이트를 **형제 모듈의 기존 형태와 대조**한다.

이유: 형태 판정은 취향이 되기 쉽다. 형제와 대조하면 "이 프로젝트에서 낯선 형태인가"라는 검증 가능한 질문이 된다. ⛔ 형제가 3+ 곳에서 같은 형태면 그게 관례다 — 관례를 위반으로 지적하지 않는다(`skills/arch-critic/SKILL.md` §분석 제약).

⛔ **반대 방향도 같이 묻는다 — 관례라는 판정이 면제가 되지 않도록.** 위 규칙만 두면 형제와 같다는 사실이 정당화로 굳는다. 형제의 형태에는 그것을 정당화한 근거가 있고, 그 근거가 이 대상에도 성립해야 이전된다.

| 묻는 것 | 발화 조건 |
|---|---|
| 형제의 그 형태를 요구한 근거가 무엇인가 | 형태를 형제에서 가져왔을 때 |
| 그 근거가 이 대상에서도 성립하는가 | 위 근거가 형제 **자신의 속성**일 때 |

근거가 형제 자신의 속성이면(그 파일이 쓰는 심볼·그 화면의 레이아웃 제약·그 타입의 소비처) 형태만 옮기는 것은 답습이다. 근거 축을 **레이아웃 제약·정책·데이터** 중 하나로 태그하고, 태그가 대상에서 달라지면 이전하지 않는다 (`modules/promotion-ledger.md` **L-12** 의 근거 태깅과 같은 기계).

⛔ 두 방향은 **쌍이다.** 한쪽만 적용하면 판정이 반대편으로 기운다 — 관례 존중만 남으면 답습을 못 잡고, 이전 가능성만 남으면 정당한 관례를 위반으로 지적한다.

## 4. 경계 문구 (필수)

브리프에 **이 문장을 반드시 포함한다**:

> *"버그·회귀·크래시는 다른 리뷰어가 담당한다. 너는 '이 코드가 취할 수 있는 더 나은 구조'만 본다. 동작은 맞다 — 그런데 이 형태가 최선인가?"*

근거: A/B B군이 이 문장과 함께 severity `minor 7 / suggestion 3 / major 0`을 냈다. **결함 판정을 하지 않았다.** 이 문장을 빼면 구조 렌즈가 결함도 판정하려 하고, 결함 렌즈와 중복·충돌한다.

## 5. ablation 기록

⚠️ **5축은 실제로 7개 독립 판정이다** (A 1 + B 1 + C 1 + D 3 + E 1). 축 이름이 실행 규칙 수를 줄이지는 않는다.

⚠️ *[candidate: evidence 1 session — 통제 A/B 1건. 축별 load-bearing 미측정]*
활성 강제 없음. 리뷰 실행마다 **축별로** 기록하고 3~5 세션 후 neutral 축 제거 또는 병합을 판정한다.

| 기록 항목 | 왜 |
|---|---|
| 축별 발견 수 | 어느 축이 실제로 이슈를 만드는가 |
| 축별 신규성 (결함 렌즈 미포착 여부) | 축이 없으면 놓쳤을 것인가 |
| 축별 토큰 | 비용 대비 |

표기 규약 (⛔ 축을 묶어서 세면 어느 축이 일하는지 알 수 없다):

```
축A: evidence 2 sessions (PR, PR) / 축B: evidence 1 session (PR)
```

**축별로 분리해 세고, 카운트를 혼합하지 않는다.** — 이 형식이 필요한 전부다 (`modules/review-checks.md` 4-N과 동형이지만 그 파일을 Read할 필요는 없다).

## 6. craft 축 F~J — craftAxes 옵션 전용

> ⛔ 기본값은 스킬마다 다르다 — fz-peer-review 는 §2 의 기본 브리프(§3 + §4)에 §6 을 더하고(`craftAxes:false` 로 끈다), fz-review 는 `craftAxes:true` 로 부를 때만 더한다. Lead 가 직접 적용하는 경로(Tier 0/1 · fz-review light)도 그 스킬의 기본을 따른다.

craft 축은 **결함이 아닌 솜씨**를 본다. 동작은 맞는데 이 프로젝트의 규칙·관례나 언어 관용과 어긋나는 자리다. 축 목록은 품질 fixture 의 채점 축(`tests/fixtures/quality` · SC-4)과 같고, 여섯 중 `design_alternative` 는 위 B 가 이미 묻는다.

| craft 축 | 모듈 축 |
|---|---|
| `idiom` | F. 관용 |
| `naming` | G. 네이밍 |
| `architecture` | H. 아키텍처 규칙 |
| `ui_structure` | I. UI 구조 |
| `placement` | J. 배치 |
| `design_alternative` | B. 구조 대안 ≥2 |

⛔ 이 표의 첫 열은 `workflows/peer-review.js` · `workflows/review-live.js` 의 `CRAFT_AXES` 와 같은 목록·순서다. `tests/workflows/craft-axes.js` 가 두 워크플로와 이 표, 품질 fixture 검사기의 축 목록을 대조한다.

### F. 관용

이 언어·프레임워크에서 **흔히 쓰는 표현**을 쓰는가. 같은 일을 하는 관용 형태가 있으면 그 형태와 줄 수 차이를 제시한다.

이유: 관용에서 벗어난 코드는 동작해도 읽는 사람을 한 번 더 멈추게 한다. E(코드 형태)가 형제와 대조한다면 F 는 언어의 관용과 대조한다.

### G. 네이밍

이름이 **역할 · 도메인 어휘 · 프로젝트 명명 규칙**과 맞는가. 맞지 않으면 바꿀 이름과 근거(규칙 레코드 · 형제 이름)를 제시한다.

이유: 이름은 컴파일러가 검증하지 않는다. 규칙(`…DTO` 접미사 같은)이 있으면 지적이 검증 가능해진다.

### H. 아키텍처 규칙

**의존 방향 · 레이어 규칙**을 지키는가. 프로젝트가 선언한 방향을 거스르는 호출을 찾는다.

이유: A·D 는 구조가 좋은지를 묻고, H 는 이 프로젝트가 **정한 규칙**과 맞는지를 묻는다. 규칙 레코드가 없으면 H 로 지적하지 않는다.

### I. UI 구조

화면 구성이 규칙·형제와 맞는가 — **상태 소유(누가 만들고 누가 받는가) · 뷰 책임 · UI 프레임워크 선택**을 본다.

이유: UI 상태 소유가 틀리면 화면이 다시 그려질 때 상태를 잃는다. 빌드와 테스트는 이것을 잘 잡지 못한다.

### J. 배치

코드가 **놓인 모듈 · 폴더 · 레이어**가 맞는가. 이미 있는 공용 코드를 다시 만들지 않았는가.

이유: 잘못 놓인 코드는 다음 사람이 찾지 못해 다시 만든다. 공용 유틸의 재구현도 J 로 잡는다.

### severity 와 규칙 인용

- 규칙 레코드(`projectRulesPath` — `modules/project-rules.md`)를 `ruleRef` 로 인용할 때만 **minor 이상**이다
- 규칙 없이 낸 craft 지적은 **suggestion 까지**다 — 취향을 결함처럼 올리지 않는다
- 규칙 레코드가 없으면 워크플로가 "규칙 인용 지적 금지 — 코드 근거만" 줄을 넣는다
- 축마다 `axisCoverage` 에 1행을 쓴다(`finding` · `none` · `not_applicable`). `none` 과 `not_applicable` 도 note 에 이유를 쓴다 — §3 머리의 "해당 없음도 이유를 쓴다" 와 같은 장치다
