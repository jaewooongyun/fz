## 1. 적용 범위

| 대상 | 이 문서 적용 |
|------|-------------|
| `review-report.md` 이슈 본문 | ✅ — 필수 필드 위에 서술을 얹는다 |
| `pr-comments.md` / 게시 코멘트 | ✅ — 톤은 SKILL.md Comment Style Guide, 구조는 여기 |
| 에이전트 JSON 산출 | ❌ **서술 형태**는 적용 안 함 — 스키마가 dedup·투표를 위해 균일해야 한다. ⚠️ 단 **대안 2개+의 *발굴*은 에이전트 소유**다(`description` 내 인코딩 — `skills/arch-critic/SKILL.md` §Alternative Design). Lead는 그 배열을 §3 C4 성격 라벨로 **재서술**한다 |

**필드와 원칙은 대립하지 않는다.** 필드(`File:line`·`Origin`·`Confidence`·`Found-by`)는 *어떤 정보가 있어야 하는가*이고, 원칙은 *그 정보를 어떻게 엮어야 리뷰어가 따라오는가*이다.

## 2. 원칙 3

### 원칙 1. 리뷰어가 그 코드를 안 읽고도 결함을 재구성할 수 있어야 한다

리뷰어는 당신이 읽은 SDK 소스도, base 브랜치 코드도 안 읽었다. "A 때문에 B, B 때문에 C"의 **각 화살표에 `파일:줄`이 붙어야** 따라올 수 있다.

화살표에 근거가 없으면 리뷰어가 할 수 있는 건 믿거나 안 믿거나 둘뿐이고, 대개 안 믿는다.

### 원칙 2. 확정과 미확정을 문장 수준에서 갈라라

한 문단에 섞이면 리뷰어가 **어디까지 믿고 어디부터 확인할지** 판단할 수 없다.

Synthesize가 이미 `Origin`(regression/pre-existing/improvement)과 `Basis`(CV=code-verified / IO=inference-only)를 계산해 뒀다. 그 판정을 글에도 살린다 — 매트릭스에만 남기고 본문에서 뭉개면 계산한 의미가 없다.

### 원칙 3. 제안에는 "무엇을 보장하는지"까지 써라

대안이 둘이면 리뷰어는 **성격**을 알아야 고른다. "근본 해결이지만 구조 변경"과 "한 줄이지만 안전망"은 선택 기준이 다르다. 무엇을 고치는지만 쓰고 무엇을 보장하는지 안 쓰면, 리뷰어는 두 대안을 비교할 축이 없다.

## 3. 형태 예시 4종

> ⛔ **게이트가 아니다.** 넷 다 PR 한 건에서만 검증됐다. 결함 모양이 다르면 벗어나도 된다.
> 다른 형태가 더 맞는데 여기 맞추려 애쓰는 순간 이 문서는 해가 된다.

| # | 형태 | 어떤 결함에 맞나 |
|---|------|-----------------|
| C1 | **소진 증명표** — 후보 → 실제 코드 → 결과 | "~할 방법이 없다" 같은 **부정 주장**. "없다"는 후보를 나열하고 하나씩 닫아야 증명된다 |
| C2 | **경우 전개표** — 순서/조건 → 무슨 일 → 결과 | 타이밍·순서·상태에 **의존하는** 결함 |
| C3 | **확정/조건부 2분할** | 정적 분석으로 일부만 확정될 때. 원칙 2의 구체형 |
| C4 | **대안 성격 라벨** — 근본 해결 / 안전망 | 수정 방향이 2개 이상일 때. 원칙 3의 구체형 |

## 4. Few-shot

### (1) 원칙 1 — 부정 주장은 후보를 소진해야 증명된다 [C1]

```
BAD:  "자동 전환이 실패하면 복구가 안 될 수 있습니다."
      → 리뷰어: "왜 안 되는데? 탭하면 되는 거 아냐?" — 확인할 방법이 없다

GOOD: 복구 후보를 표로 소진 —
      | 후보 | 실제 코드 | 결과 |
      | .ended 재시도 | PlayerController.swift:224-231 didPlayToEndTime 구독 | 1회성. 놓치면 끝 |
      | 위치 복원 후 탭 | seekToZero가 pause(except:)에서만 (353·368) | 인덱스 변경 시에만 |
      | 진행 콜백 감지 | 정지 상태라 didUpdateTime 미도달 | 트리거 없음 |
      → 리뷰어가 각 행을 직접 열어 확인할 수 있다
```

### (2) 원칙 2 — 확정과 조건부를 갈라 쓴다 [C3]

```
BAD:  "리스너가 해제되지 않아 누수가 발생하고, 그로 인해 다음 재생이 동작하지 않을
       수 있습니다."
      → 어디까지가 코드로 확인된 사실이고 어디부터가 추론인지 구분 불가

GOOD: **확정**: 리스너 해제 경로 없음 — Core.swift:1484-1513에 removeObserver 호출 부재
                (Basis: CV)
      **조건부**: 위 누수가 다음 재생 무동작으로 이어지는지는 이벤트 순서에 의존.
                DEBUG 로그로 판별 필요 (Basis: IO)
```

### (3) 원칙 3 — 대안에 성격 라벨을 붙인다 [C4]

```
BAD:  "Bool을 반환하도록 바꾸거나 seekToZero를 호출하면 됩니다."
      → 둘 중 뭘 골라야 하는지 판단 기준이 없다

GOOD: (a) **근본 해결 / 구조 변경**: 전환 성공 여부를 Bool로 반환 → 호출부가 실패를
          인지하고 분기할 수 있다. 호출부 3곳 수정 필요
      (b) **안전망 / 한 줄**: 실패 시 seekToZero 호출 → 최소한 처음부터 다시 재생 가능.
          근본 원인은 남는다
```

### (4) 원칙 1 — 순서 의존 결함은 경우를 전개한다 [C2]

```
BAD:  "이벤트 순서에 따라 플래그가 잘못 설정될 수 있습니다."

GOOD: | 순서 | 무슨 일 | 플래그 |
      | A→B | 전환 시작 후 완료 통지 | isChaining=false (정상) |
      | B→A | 완료 통지가 먼저 도착 | isChaining=true 잔존 ← 문제 |
      → 각 행이 재현 시나리오가 되어 리뷰어가 테스트할 수 있다
```

### (5) 엣지 — 단순한 결함에는 표를 만들지 않는다

```
BAD:  오타 하나에 소진 증명표 3행 + 대안 라벨 2개
      → 형식이 내용을 압도한다. 리뷰어 피로가 늘고 진짜 문제가 묻힌다

GOOD: "ShortsCore.swift:83 — `isChanining` 오타. `isChaining`으로 수정 (Origin: regression)"
      → 한 줄로 끝나는 결함은 한 줄로 쓴다
```

## 5. 과잉 형식화 방어

형태 4종은 **인과가 한 문장으로 안 끝날 때**만 쓴다. 판단 기준:

```
리뷰어가 "왜?"를 한 번 더 물을 것 같은가?
  아니오 → 한 줄로 쓴다
  예     → 그 "왜?"의 모양에 맞는 형태를 고른다 (부정 주장이면 C1, 순서 의존이면 C2 …)
```

⛔ 결함 수가 많을수록 형식을 줄인다. 이슈 7건에 표가 7개면 아무도 안 읽는다.

> 결함 하나가 여러 파일에 걸칠 때의 **분할 규칙**은 이 문서 소관이 아니다 — 게시 절차 문서(인라인 앵커)가 단일 출처다. 여기서는 각 조각의 *서술*만 다룬다.
