# v4.34.0 (2026-09-13) — 대조군을 넷 세우고, 자기 자신과의 대조를 빠뜨렸다 [MINOR]

`/fz-plan` 이 한 시간 넘게 걸린다는 보고에서 시작해 **3,492초를 1,344초로** 줄였다.
그런데 이 릴리즈에서 가장 값이 나간 발견은 시간이 아니다 — **구조 A/B 를 네 번 비교하는 동안
같은 구조를 두 번 돌려본 적이 없었다**는 것이다.

> ⛔ 작업 중 버전을 `4.34.0 → 4.35.0 → 4.35.1` 로 올렸다가 커밋 시점에 4.34.0 하나로 되돌렸다.
> 세 버전 모두 커밋된 상태였던 적이 없어 태그가 가리킬 트리가 없었다. CHANGELOG 의 세 절이 원래 경계다.

## 1. 원인은 한 층이 아니라 셋이었다

75~90분 보고를 실측하니 Workflow 워커(76·75·90분) · Lead 자체 생성(29~45분) · GPT 호출(11회 24분)
셋으로 갈렸다. **45분 넘은 `/fz-plan` 3건 중 Workflow 를 쓴 건은 0건**이었다.
`--deep` 은 원인이 아니다 — 스크립트에 분기가 0건이고 3건 모두 미사용이었다.

⛔ 전환점인 `fdcfe56`(렌즈 6콜 sonnet→opus + 11콜 xhigh)이 신설한 `experiment-log §5.8`
사전등록 표는 **데이터행 0** 이었다. 임계는 등록됐고 재는 주체가 없었다.

`advisor` 도 층이었다. 프롬프트 금지문으로는 9콜 중 8콜을 못 막았고,
env `CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1` 이 워커에 상속되는 것을 실증해 **-907초**를 회수했다.

## 2. 시간을 정하는 것은 과제가 아니라 구조다

같은 9콜 구조에서 과제를 *감사형* ↔ *신규구현* 으로 바꾸면 3,621초 대 3,492초로 **3.6% 차**다.
같은 트리에서 구조를 9콜 → 3콜로 바꾸면 **-65.5%** 다. wall 은 과제 난이도가 아니라
**직렬 단계 수 × 단계당 생성 시간**이 정한다.

**배선 전환**: `plan-collaborative.js`(6단계 9콜) → **`plan-lean2.js`(2단계 4콜)**.
전체 플랜 ∥ edge 적대 ∥ impact+arch 를 동시 3으로 띄우고 델타 병합 1콜로 닫는다.

| 항목 | 이전 | 이후 |
|---|---|---|
| 구조 | 6단계 9콜 | 2단계 4콜 |
| wall | 3,492초 | **1,344초 (-61.5%)** |
| 실행 가능한 command verify | 4 | **5** |

⭐ **병합 콜은 본문을 쓸 수 없다.** schema 를 `stepAmendments`·`addedEdgeCases`·`addedImpact`
**델타 전용**으로 좁혀, "다시 쓰지 마라" 를 프롬프트로 부탁하는 대신 **쓸 필드를 주지 않았다**.
여섯 단계 동안 부탁해서 안 되던 것이 한 번에 지켜졌다.

⭐ 렌즈 schema 에는 `secondaryHosts`·`existingTestSuites` 를 명시 요구했다.
찾아야 할 것에 이름을 주니 9콜도 0건이던 자리에서 7건·5건이 나왔다.

⛔ `plan-collaborative.js` 는 **존치**한다 — 롤백은 `skills/fz-plan/SKILL.md` 절차 2.5·3 의
스크립트명 한 줄이다.

## 3. 노이즈 바닥을 재지 않고 네 번 판정했다

구조 변형을 동결 워크트리 2종에서 blind 채점으로 네 번 비교했다. 매번
"9콜이 major 를 N건 더 찾는다" 가 나왔고 그것을 구조 차이로 읽었다.

⛔ **같은 구조를 두 번 돌려 서로 대조한 적이 없었다.** 뒤늦게 재니 —
같은 입력·같은 스크립트·같은 동결 트리로 9콜을 2회 실행하자 **상호 고유 major 5건**,
overall **`Q-superior`**(동등 아님), 그리고 **채택 기전까지 반대**로 갈렸다.
1회차는 rect 레지스트리 + GeometryReader, 2회차는 1회차가 *"선례 0건"* 으로 기각했던
UIViewRepresentable 마커였다. 변인은 실행 난수 하나였다.

⇒ 사전등록 임계 *"검증된 critical·major 손실 0"* 은 **도달 불가능한 값**이었고,
앞선 네 판정의 "손실 N" 은 구조 차이의 증거가 아니었다. **run-to-run 분산이 구조 간 차이보다 크다.**

임계는 *"노이즈 바닥 이하"* 로 재등록했다. ⛔ 사후 조정이 아니라 원 임계의 도달 불가능성이
실측됐기 때문이며, 재등록 주체는 사용자다.

## 5. 재는 도구가 두 번 거짓말할 뻔했다

⛔ **`claude -p` 는 백그라운드 작업을 600초에 끊는다.** 잘린 run 이 exit 0 · 오류 키워드 0건 ·
`wall=621.9s` 를 인쇄했다. baseline 대비 **-54%** 라 그대로 기록했으면 control 을 날조해
비교 전체가 무의미해졌다. 잡은 단서는 wall 이 아니라 `agents=3` 과 선언 4콜의 불일치였다.

**신설**: `fz_wf_metrics.py --expect-agents N` — `agents` 와 `journal_results` 가 둘 다 N 이
아니면 exit 1 + *"이 run 의 wall 을 기록하지 말 것"*.
`guides/skill-testing.md` §8.1 arm 설정 예시에 `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` 을
같은 줄에 넣었다 — 가이드가 권하던 명령을 그대로 따르면 22분 워크플로가 잘린다.
⛔ arm 검증 스니펫의 `max(…, key=getmtime)` 도 교체했다. **바로 위 문단이 '재현 함정' 으로
경고하는 방식을 스니펫 자신이 쓰고 있었다.**
