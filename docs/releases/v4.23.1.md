# v4.23.1 — 배선 복구: 정의된 팀의 2/3이 안 돌고 있었다 (2026-08-10)

## 배경 — 사용자가 잡은 한 줄

TVING iOS 작업 중 Swift `enum`의 계산 프로퍼티 `switch`가 이렇게 남았다:

```swift
case .poster: return Metric.posterHeight            // 상수
case .meta: return 15                               // ← 리터럴, 혼자 다름
case .mainBannerPhone, .mainBannerTablet: return Metric.mainBannerHeight  // 상수
```

외부 리뷰가 *"계획서 Descope에 '`.meta` 상수화 제외'라고 썼는데 구현이 포함함"* 이라 지적했고, Lead가 그것을 수용해 `.meta`만 되돌리면서 생겼다. **빌드 통과 · 값 동일 · 관련 테스트 0건** — 자동 oracle이 전부 침묵했고 사용자가 육안으로 발견했다("상수로 해야지 거기만 하드코딩으로 하면 어떻게 해").

이 릴리즈는 그 사건의 하네스 처방이다. 다만 **최초 진단이 틀렸고 그 정정이 본체의 절반**을 차지한다.

## 1. `code-pair` impl-quality 배선 복구 — 본 릴리즈의 실질

**문제**: `guides/agent-team-guide.md` §팀 구성은 `code-*` 파이프라인의 실질 워커(opus)를 **`review-arch` · `impl-quality` · `review-correctness`** 로 정의한다. 그러나 Wave 3 Workflow 전환에서 `workflows/code-pair.js`는 **`review-arch` 하나만** 스폰했다.

**대조군이 판정을 굳힌다** [verified: `grep -oE "agentType: 'fz:[a-z-]+'" workflows/*.js`]:

| Workflow | 가이드 정의 팀 | 실제 스폰 | 일치 |
|---|---|---|---|
| `plan-collaborative` | plan-structure + impact/edge-case/review-arch | **5개 전수**(+direction) | ✅ |
| `review-live` | review-arch + quality/correctness/counter | 3개 | ~ |
| **`code-pair`** | impl-correctness + **arch·impl-quality·correctness** | **2개**(arch만) | ⛔ |

`agents/impl-quality.md`가 소유한 책임이 *"Codebase Pattern Consistency — 기존 코드베이스의 유사 구현과 비교 / 새 패턴 도입 시 기존 패턴과의 충돌 확인 / `Grep`으로 동일 패턴 사용 사례 확인"* 이다. **사건이 정확히 그 렌즈가 봤어야 할 결함**인데, 그 렌즈가 실행 경로에서 스폰되지 않고 있었다.

⛔ 코드 주석의 근거(`code-pair.js` *"impl-quality/review-correctness/memory-curator: Lead 경로 (S4 결정 — 미포함 기본값)"*)는 **문서로 추적되지 않는다** — 릴리즈 노트 서술 0건 [verified: `grep -rn "impl-quality" docs/releases/`].

**조치**:
- Stage 2를 **full 모드에서 `review-arch` + `impl-quality` 병렬 2렌즈**로 확장
- 두 렌즈 결과를 **단일 `review` 객체로 병합** — `s2` 완주 판정 · Stage 3 조건 · `residualIssues` 세 곳이 참조하는 하류 계약을 보존한다. 한쪽 null이면 다른 쪽 단독으로 진행하고 `log`에 명시
- `impl-quality` 프롬프트에 **형제 균일성 게이트 + 소비처 축 제외**를 인라인(§2의 오탐 실측 반영)
- `light`(fz-fix)는 **arch 단독 유지** — 비용 보존. `opus` 동시 ≤2 (+Lead=3) governance 상한 내
- call 수 서술 3곳 동기화: `meta.description` 1-3→1-4 · 헤더 주석 · `fz-code` 절차 3

> ⚠️ **A만으로 완결이 아니다**: `impl-quality`는 cross-file 광역 렌즈라 *같은 블록 형제 슬롯* 입도는 여전히 없다. 그 부분이 §2다.

## 2. 검증 4-P 신설 (candidate) — 오탐 실측이 절차를 바꿨다

`modules/review-checks.md`에 **4-P Post-State Consistency**를 신설했다. 묻는 것은 *"편집 라인이 놓인 **자리**가 일관적인가"* 이며, `fz-review` 검증 목록·완료 체크리스트에 참조를 걸었다(4-N/4-O와 동일 candidate 형식).

**초판 절차를 실제 Swift 워크트리에 적용한 결과** — peer slot **11곳** → emit **9곳** 중 진짜 결함 **1곳**(재구성한 사건 자체). 오탐의 공통 형태는 *표현 비대칭이 **의미 비대칭**을 정확히 반영*하는 경우였다. 이를 절차에 반영했다:

| 추가 관문 | 근거 |
|---|---|
| **step 2 형제 균일성 게이트** — 비교 축에 대해 형제가 이미 균일할 때만 진행, 불균일이면 **중단·보고 금지** | `BannerMainCell+LayoutConstant.swift` 형제 15개가 `adapted` 13 / `iPadOrNot` 5 / stored `let` 1 — **4형태 혼재**. 게이트 없으면 전량 오탐 |
| **step 3 소비처 의존 축 제외**(접근수준·상수 소유권) | `liveIcon`이 non-private인 근거가 **다른 파일**의 프로토콜 요구(`BandCell.swift`)에 있다. `Metric` public 정당성 판정에는 리포 grep 4회가 필요했다 ⇒ **in-block 판정 원리적 불가** → 4-E 소관 |
| **step 4 의미 비대칭 면제** | 값 결정 규칙(연속 스케일 vs 브레이크포인트) · 조건부 포함 vs 단순 옵셔널 · 타입 강제(`nil`·`.zero`) |
| **step 5 tie-break** — provenance 랭킹(코드 현실 > 자작 초안 문서) | 검출이 처방을 정하지 않는다. 이 규칙이 없으면 비대칭을 감지하고도 *"계획서에 그렇게 썼으니 둔다"* 로 합리화 가능하다 — **사건 당시와 같은 결론** |

**철회한 초판 주장 2건**:
- ⛔ *"같은 파일·같은 블록이라 **비용 0**"* → 거짓. 위 실측대로 타 파일 Read·리포 grep이 실제로 필요했고, 형제 집합 크기도 7줄~85줄로 편차가 크다. 사건이 우연히 *작고 자기완결적인 switch*였기에 0처럼 보였다
- ⛔ *"기계 검증이 **원리적으로** 불가"* → 과장. magic-number 계열 lint가 결정론적으로 잡는 부류다. **"현행 fz 게이트(빌드·테스트·swift-format)로는 침묵"** 이 참인 진술이며, **lint 대안 검토는 선행 과제**로 남는다

⛔ **diff 앵커링 상속**: 절차가 "편집 hunk"에서 출발하므로 **편집이 닿지 않은 기존 비대칭은 보이지 않는다** — 극복 대상이던 한계를 그대로 물려받았다.

## 3. "축 부재" 진단 철회 — 자기 재현 기록

초판은 이 관찰을 `harness-engineering.md` **§5 "원칙 8"** 로 신설하며 *"편집 지점의 형제 관계를 보는 렌즈가 **어디에도 없다**"* 고 단정했다. **거짓이다** [verified: grep] — 형제 렌즈가 **6개** 실재한다:

| 렌즈 | 위치 | 성격 |
|---|---|---|
| **Sibling-Convention Check** | `skill-authoring.md` §1 | *"동류 항목의 표기 템플릿을 먼저 grep해 일치시킨다"* — **동일 실패 모드**, **이미 candidate 등재** |
| 패턴 일관성 | `fz-review` §검증 1 | *"Grep → 변경 후 패턴 일관성"* — 3중 리뷰 첫 축이 delta-only가 아니다 |
| Codebase Pattern Consistency | `agents/impl-quality.md` | 구현 중 실시간 감시 **전담 소유자** |
| 그 외 3 | `codex-skills/fz-reviewer` · `modules/evidence-collection.md` · `agents/review-direction.md` | 동일 축 |

**정확한 진단** = **(a) 입도 부족**(광역 렌즈뿐, *같은 블록 형제* 단위 없음) + **(b) 소유자 미배선**(§1).

> ⛔ **자기 재현**: 이 오진 자체가 그 관찰이 겨냥한 실패 모드다 — **기존 규칙을 3개로 스스로 한정해 조사**하고 커버리지 실측 없이 "홀 판정 성립"을 선언했다. *대상을 격리해서 보고 그것이 속한 구조를 보지 않은* 것. 진단이 바뀌면 처방도 바뀐다: 신설이 아니라 **배선 복구가 먼저**였고, `harness-engineering` 원칙 1(가장 단순한 해결책 먼저)이 요구하는 대안 비교가 선행되지 않았다.

### 3-1. §5 원칙 8 → §12 R8-A 강등

`harness-engineering.md`는 헤더와 §설계 원칙에서 *"Anthropic 공식 엔지니어링 블로그, arxiv 논문, 오픈소스 구현체를 기반으로 정리"* · *"공식/학술/고품질 출처만 인용"* 을 **자기 편집 정책**으로 명시한다. §5 원칙 1~7의 근거를 전수하면:

| 원칙 | 근거 |
|---|---|
| 1·5·6 | Anthropic 공식 (2026.03 / 2025.11) |
| 2·7 | H1 (Anthropic Labs) + platform.claude.com `[verified]` |
| 3 | NLAH 논문 |
| 4 | Generator≠Evaluator (외부) |
| **8 (초판)** | **자체 세션 관측 1건** |

원칙 번호를 점유하면 하류 3파일이 이를 **동급 권위로 인용**하게 된다. 경고 문구를 붙여도 번호 자체가 그것을 상쇄한다.

**조치**: §5에서 제거 → **§12 "하네스 홀 candidate ↔ 외부 수렴 근거" 표에 `R8-A` 행**(외부 근거 열 = **미대조**) + 하위 절 *"내부 관측, 권위 아님"*. 하류 참조 8곳을 `§12 R8-A`로 일괄 갱신 [verified: `§5 원칙 8` 잔존 0].

부수 정정: **"세 축" 프레이밍 → 스코프 × 질문 격자**. 앞 두 칸은 *어디를 보는가*(diff 안/밖), 세 번째는 *무엇을 묻는가*(옳은가/일관적인가)라 직교하지 않는다 — post-state는 별도 축이 아니라 **(diff 안 × 일관성) 셀**이다.

## 5. 검증 구성 — Codex 부재 하의 3렌즈

Codex probe 실패(`out of credits` — **산출 0 + exit 0**이라 규약상 probe 미성립) [verified: 호출 직전 probe 1회 실행, 기록 기반 선제 생략 아님]. `fz-review` 규약의 **Codex 불능 분기**대로 fresh-context Agent로 대체하되, **서로 다른 질문**으로 3개를 띄웠다:

| 렌즈 | 질문 | 그 렌즈만 잡은 것 |
|---|---|---|
| 설계 비평 (premise-challenge, ledger L-11 요구) | *"진단 전제 자체가 틀렸을 가능성은?"* | **§3의 오진** — 기존 렌즈 6개 실재 |
| 규약 감사 | *"fz 자신의 문서화된 규칙을 지켰나?"* | **§4의 집행 결함 5건** |
| 실효성 검증 | *"실제 Swift 코드에 돌리면 뭐가 나오나?"* | **§2의 오탐 8/9 + "비용 0" 반증** |

⛔ **동종 검증이다** — 3렌즈 전부 Claude이므로 **cross-model 안전망은 부재**한다. Codex 회복 시 R8-A/4-P를 교차 채점에 올려야 `§5.5` 규율 2("self-preference 단독 채택 금지")가 실질 충족된다. 그때까지 R8-A는 문서상 **가설**로 표기된다.
