## 1. 게이트 원장 — 완료 기준을 파일에 적는다

`/fz-plan` 이 계획의 `steps[].verify` 를 읽어 `{WORK_DIR}/gates/plan.md` 를 만든다.

```
- [ ] S1: 빌드가 통과한다
  CRITERION: 시뮬레이터 빌드가 성공해야 한다
  CHECK: xcodebuild -workspace ... build
  EXPECT: BUILD SUCCEEDED
  APPROVED_ORACLE_HASH: 4e7e65bdc54c
  EVIDENCE: pending
```

판정 계약은 **exit 0 그리고 EXPECT 매치**다. 하나만 만족하면 미통과다. exit 0 만 보면 "실행됐다"만 증명하고, EXPECT 만 보면 실패한 프로세스가 에러 텍스트에 성공 토큰을 담고 있을 때 통과한다.

눈으로 봐야 하는 항목은 `MANUAL:` 로 적는다. 억지 command 보다 정직한 manual 이 낫다. `--confirm` 은 TTY 에서만 동작하므로 모델·hook·워커는 스스로 확인할 수 없다.

exit 은 네 갈래다 — `0` 충족 · `1` 미충족 · `3` 원장 계약 위반 · `2` 인프라. **판정의 fail-open 은 금지하고 인프라 부재의 fail-open 은 허용한다.** timeout 과 출력 초과는 exit 1 이다. 시간이 없었다는 것은 통과가 아니다.

**오라클**: fixture 66케이스 16범주. 기대 exit · 산출물 내용 · 시간 · stdout · stderr 다섯 축.

## 2. 배선 5지점

| 시점 | 하는 일 |
|------|--------|
| fz-plan Phase 3.1 · 4.5 | draft 원장 생성 → Codex 판정 반영 → `--finalize` 확정 |
| fz-code 절차 6.4 | `--only {StepID}` 로 해당 Step 게이트만 실행 |
| fz-review Phase 5.5 | `--reverify` 로 기록된 증거를 불신하고 재실행 |
| 세션 종료 | Stop hook 이 미충족 원장에서 종료를 막는다 (사용자 설치) |
| `/fz-manage check` | 원장 상태 노출 — hook 미설치 머신의 유일한 경로 |

⛔ 호출은 `${FZ_PLUGIN_ROOT}` 절대 경로다. 상대 경로는 설치된 플러그인에서 대상 레포에 파일이 없어 exit 2(인프라 통과)로 **강제력이 조용히 사라진다.**

⛔ `--only` 가 없으면 첫 Step 에서 영구 정지한다. 전체를 돌리면 아직 하지 않은 미래 Step 게이트가 실패하기 때문이다.

원장이 없는 세션에는 아무 영향이 없다. 게이트를 쓰지 않던 흐름은 그대로 돈다.

## 3. 위조를 막는 세 층

**증거 서명.** `EVIDENCE:` 의 `sig=` 가 그 게이트의 oracle · exit · 출력에 묶인다. 판정기가 다시 계산해 대조한다. 원장을 쓰는 것도 모델이므로 `- [x]` 로 바꾸고 통과 텍스트만 적는 경로를 막는다.

⛔ **암호학적 위조 방지가 아니다.** 알고리즘이 공개돼 있어 작정하면 재계산할 수 있다. 막는 것은 *우연한* false-green 이다.

**승인 도장.** Codex 가 "이 `CHECK` 가 제목이 말하는 것을 재는가"를 판정한 뒤 `--finalize` 가 `APPROVED_ORACLE_HASH` 를 찍는다. 그 뒤 `CHECK`·`EXPECT`·`CWD`·`TIMEOUT`·`CRITERION`·제목 중 하나라도 바뀌면 exit 3 이다.

확정본에서 **부분 도장은 exit 3** 이다. 도장이 있으니 보호받는다고 읽히는데 안 찍힌 게이트는 CHECK 를 바꿔도 통과한다 — 무도장보다 위험하다.

**파서 fail-closed.** 헤더 중복 · 게이트 밖 들여쓰기 속성 · plan 의 개행 인젝션 · ROOT 소유 위반을 거부한다. 특히 헤더 중복은 실질 false-green 이었다 — `STATE: closed` 를 한 줄 append 하면 원장 전체가 no-op 이 되고, `ABANDON:` 처럼 흔적이 남는 이탈로가 아니라 **조용한 무력화**다.

## 4. 승인 해시와 증거 서명을 분리했다

`oracle_hash` 에 `SHELL` 과 `PATH` 가 들어 있었고 그 해시가 승인 도장의 비교 대상이었다.

```
fz-plan  세션 A: --finalize → 도장 = sha(… | PATH_A | SHELL_A)
fz-code  세션 B: --only S1  → 실측 = sha(… | PATH_B | SHELL_B)   → exit 3
```

PATH 만 바꿔도, SHELL 만 바꿔도 exit 3 이다. 메시지는 "승인 후 oracle 이 바뀌었다"라며 원인을 잘못 지목한다. fz-plan → fz-code 가 별 세션인 것은 예외가 아니라 설계된 흐름이다(compact · 다음 날 · 다른 터미널 · direnv/nvm shim).

증거 서명도 같은 병이었다. 다른 PATH 로 `--status` 를 돌리면 통과한 게이트가 **UNMET** 으로 읽혔다.

두 해시의 목적이 다르다.

| 해시 | 무엇을 묶나 | 환경 |
|------|------------|:----:|
| 승인 도장 | 사람·Codex 가 승인한 oracle | ⛔ 제외 — PATH 는 승인 대상이 아니다 |
| 증거 서명 | 이 결과가 어느 환경에서 나왔나 | ✅ 포함 (단 **기록된** 값으로 재계산) |

증거 필드 `path=` 를 `env=` 로 바꾸고 서명에 묶었다. 이전엔 기록만 되고 서명 밖이라 provenance 가 실제로 보호되지 않았다.

**부수 이득** — 승인 해시가 머신 독립이 되어 정적 fixture 에 유효한 도장을 넣을 수 있다. 이전 더미 `000000000000` 은 "불일치"가 아니라 "아무 값과도 불일치"를 보고 있었다.

## 5. Stop hook — 산문 배선의 재귀를 끊는다

배선 1~3은 SKILL.md 산문이라 Lead 가 건너뛰어도 신호가 없다. 이 도구가 대체하려던 것이 산문 강제인데 **그 도구를 부르는 것 자체가 산문**이었다.

차단 계약은 공식 `plugin-dev` 스킬에서 실측했다.

```
입력: {"session_id":…, "transcript_path":…, "cwd":…, "hook_event_name":"Stop"}
차단: stderr ← {"decision":"block","reason":"…"}  +  exit 2
```

⛔ `hookSpecificOutput.decision` 도 `{"continue":false}` 도 아니고 **top-level `decision`** 이다. 세 후보 중 어느 것인지 문서로 확정했으므로 live 세션 probe 가 필요하지 않았다. "live 세션이 필요하다"고 판단해 한 라운드 미뤘던 것이 틀린 판단이었다.

설계 결정 셋 — 원장 발견은 `cwd` 하위 glob(세션 바인딩은 쓰는 쪽 배선이 필요해 조용히 무력화될 위험) · 판정은 `--status`(재실행은 게이트당 120초로 hook 에 부적합) · 전면 fail-open("세션 감금이 게이트 누락보다 나쁘다"가 가장 날카로운 자리).

무한 루프 방어 — Stop 을 막으면 Claude 가 계속하고 다시 Stop 에 도달한다. 같은 상태로 **2회**까지만 막는다. 상태를 못 쓰면 즉시 통과 — 방어 없이 막으면 무한 block 이다.

⛔ **자동 배선하지 않는다.** `examples/hooks.json.example` 의 Stop 항목을 `.claude/settings.json` 으로 복사해야 발동한다. 따라서 **기계적 차단은 설치한 머신에만 있다.** 원장·판정기·배선 1~3은 어디서나 동작한다.

**오라클**: `--self-test` 14케이스. 깊이 1~4 · draft-only · skip-git · approved · kill-switch · 오배선 · bad-cwd · env-missing · loop-guard. health-check 2.6 에 배선.

## 7. ⛔ 열다섯 번 만난 실패 — 코드는 있는데 발화하지 않는다

이 릴리즈에서 가장 값진 발견이다. 표면이 다섯 가지였다.

| 표면 | 없던 것 |
|------|--------|
| `codex_gate_verdict_schema` | `--output-schema` 로 넘기는 호출부 |
| `codex_verification_schema` | 유효성을 보는 lint |
| `APPROVED_ORACLE_HASH` 검사 3곳 | 필드를 **발급**하는 코드 |
| strict 준수 요구 | 검사(`#N10`) |
| Stop hook `_block()` | **exit 코드가 밖으로 나가는 경로** |

마지막이 특히 선명하다.

```python
try:
    sys.exit(main())              # SystemExit 을 던진다
except BaseException as exc:      # ⛔ SystemExit 도 BaseException 이다
    sys.exit(EXIT_PASS)           # → 항상 0
```

최후 방어("어떤 예외도 세션을 감금하지 않는다")가 자기 exit 을 삼켰다. `decision=block` JSON 은 stderr 로 나갔는데 exit 은 0 이었다.

⭐ **다섯 다 문법이 정상이고 테스트도 통과했다. 정적 검사로는 하나도 안 잡혔고, 전부 1회 실행으로 드러났다.**

값싼 검출 — 선언된 산출물은 **1회 실행**이 완료 조건이다. 언급 수·존재 여부는 오라클이 아니다. 특히 "실행 경로 0건"으로 진단한 결함을 고칠 때는 **같은 기준**을 수정에 적용한다. 그리고 조건부 검사(`if X:`)를 쓸 때 X 를 **만드는** 코드를 grep 으로 확인한다.

## 8. ⛔ 열 번 만난 실패 — 테스트가 자기 이름의 축을 못 본다

| 사례 | 못 본 이유 |
|------|-----------|
| forgery fixture 4종 | `exit`/`mutates` 두 축으로는 같은 exit 을 내는 방어선이 구분 안 됨 |
| ROOT 검사 4종 | 전부 exit 3 이라 어느 검사가 발화했는지 모름 → `expect_stderr` 축 신설 |
| 소유 검사 | 관측하는 fixture 가 **하나도 없었다**(제거해도 37/37) |
| `writeback-sibling-edited` | `sed` 패턴이 **자기 CHECK 줄에도** 있어 자기를 고쳤다. 이름은 sibling 인데 `oracle-changed` 와 같은 축을 봤다 |
| `exec-late-descendant` | 지연 2초일 때 옛 코드가 **타이밍으로 통과**(스레드 2개 × 1초 join) |
| 문서 수치 치환 | `str.replace` 가 앵커 불일치 시 조용히 원본을 반환하는데 성공 메시지는 *계산값*을 찍었다 |
| 스키마 수정 스크립트 | 수정과 재검산이 **같은 술어**(`type == "object"`)를 써서 nullable 변형을 함께 놓쳤다 |
| Stop hook glob | fixture 가 정확히 깊이 2로만 원장을 만들어 깊이 1·3·4 미관측 |
| `loop-guard` | 상태 누적 방어는 **1회 발사**로 관측되지 않는다 |
| `--oracle-fields` 한계 | "관측 불가"라 기록한 그 한계가 **cross-session 차단 결함의 증상**이었다 |

값싼 검출 여덟 가지가 나왔다.

1. **방어선을 개별로 제거해** 각각 어느 테스트가 잡는지 확인한다. 통합 주입은 총계만 보여 "N종 중 M종만 관측"을 숨긴다
2. 같은 exit 을 내는 검사가 둘 이상이면 결과 코드로 구분하지 않는다 — 거부 *사유*를 assert 한다
3. 테스트의 setup 동작이 관측 대상 밖만 건드리는지 확인한다
4. 타이밍 테스트는 옛 동작의 한계값 2배 이상으로 잡는다
5. `replace` 계열은 치환 건수를 assert 한다. 성공 메시지에 *계산값*이 아니라 *관측값*을 찍는다
6. 수정과 검산은 술어를 공유하지 않는다. 검산이 더 넓은 술어를 쓰고, 수정은 고정점까지 반복한다
7. 경로·깊이·이름에 패턴을 쓰는 코드는 그 패턴의 **경계마다** fixture 를 만든다
8. "이 축은 관측 불가"라고 쓸 때 **왜 불가인지** 한 번 더 묻는다. 불가 사유가 대상의 *성질*이면 한계이고, 대상의 *결함*이면 고칠 것이다

## 9. 원 계획 16항목 중 15개 — 마지막은 폐기

`--merge` + BATCH shard manifest 가 마지막 미결 항목이었다. 실측하니 전제가 바뀌어 있었다.

```
execution-modes.md BATCH 절     10건
experiment-log BATCH 기록         0건
/batch 스킬                       0개
BATCH 경로의 게이트 배선           0건
```

⛔ 소비자가 없다. hook 이 각 worktree 에서 그 안의 원장을 이미 찾으므로 병합 없이도 독립 판정된다. §7의 열여섯 번째가 되지 않게 폐기했다.

unlazy 메커니즘 8종 중 6종을 채택했다. Depth Tree 는 fz 가 Step 평면 구조라 범위 밖으로 판정했고, BATCH merge 는 위 사유로 폐기했다.

unlazy 에 없는 것 6종을 추가로 만들었다 — 증거 서명 · 환경/승인 해시 분리 · `verify-gates` · `--verdict-check` · lint `#N10` · 도달성 trace(`FZ_GATES_TRACE`). 전부 리뷰와 검토가 드러낸 결함에서 나왔다.
