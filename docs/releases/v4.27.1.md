# v4.27.1 — 리베이스 스킬은 플러그인 밖에서 게이트 없이 돌고 있었다 [PATCH]

- 날짜: 2026-08-31
- 변경: `skills/fz-rebase/SKILL.md` · `scripts/verify-rebase.sh` · `scripts/test-gates.sh`
- 회귀: 73 → 78 assertion

## 이 릴리즈의 성격

"이 스킬만 팀원에게 줘도 되는가" 를 확인하는 작업으로 시작해, **줄 수 없는 상태였다**는 것을
확인하고 끝났다. 개인 경로도 개인 메모리 참조도 0건이었는데 정작 스킬이 동작하지 않는다.

---

## 1. 경로가 안 풀리면 게이트 네 개가 통째로 무산된다

SKILL.md 는 스크립트를 이렇게 가리키고 있었다.

> `<FZ_ROOT>` = fz-plugin 루트 (예: `claude plugin path fz` 결과). 사용자가 본인 설치 경로로 치환.

플러그인이 없는 사람에게는 그 명령이 실패한다. 그러면 `$VR` 이 정해지지 않고, 워크플로의
`snapshot` · `check` · `audit` · `prepush` **네 호출이 전부 무산된다.** 남는 것은 산문뿐이고,
그 상태의 스킬은 게이트 없는 리베이스 안내서다. 실패가 조용하다는 게 특히 나쁘다 — 멈추는 게
아니라 게이트 없이 진행될 수 있다.

⛔ `${CLAUDE_PLUGIN_ROOT}` 는 답이 아니다. 스킬 폴더만 `~/.claude/skills/` 에 두는 배포에서는
플러그인이 아니라 그 변수 자체가 정의되지 않는다.

답은 이미 생태계 안에 있었다. `modules/cross-validation.md` 가 규정한다 — 스킬 주입 헤더
`Base directory for this skill: …` 를 읽어 경로를 얻는다. fz-rebase 는 fz-codex 보다 **덜**
필요하다. 플러그인 루트가 아니라 자기 스킬 디렉토리만 있으면 되므로 `../..` 조차 없다.

⛔ 헤더가 없으면 추측하지 않고 묻는다 (fail-closed). 잘못된 경로로 진행하는 것보다 멈추는 게 낫다.

## 2. 개인 브랜치의 force-push 권한이 예시로 박혀 있었다

> 예: `feature/tvod` 는 사용자 소유 롱텀 브랜치라 `upstream` 으로의 force-push 가 예외적으로 허용된다.

특정 개인이 특정 브랜치에 가진 권한을, **되돌릴 수 없는 연산 바로 옆에** 적어 두고 있었다.
같은 전제가 push 승인 문구와 Will Not 목록에서 두 번 더 반복된다. 완화 문장이 붙어 있지만
그건 산문이지 게이트가 아니다 — `prepush` 는 원격 이름으로 분기하지 않는다.

세 곳을 조건 서술로 바꿨다. 핵심은 **"이 스킬은 그 승인을 확인하지 않는다"** 를 명시한 것이다.
코드가 막지 않는다는 사실을 문서가 숨기지 않게 됐다.

## 3. base 자동 해석은 오답을 준다 — 실측이 반대했다

`${PRIMARY}/develop` 하드코딩을 `git symbolic-ref refs/remotes/*/HEAD` 로 대체하려다 멈췄다.

```
origin/HEAD    → main       (실측 리포에서 7개월 정지)
upstream/HEAD  → main       (릴리스 머지만 올라옴)
upstream/develop            (실제 개발 tip)

develop 전용 커밋 49  /  main 전용 커밋 0
```

remote HEAD 가 가리키는 브랜치가 **배포 전용**인 리포가 있다. 그 위로 리베이스하면 개발
브랜치의 커밋이 base 에서 빠진 채 **게이트가 전부 통과한다** — 세 버킷은 "base 대비 보존" 만
보고 "base 가 옳은가" 는 보지 않기 때문이다.

⛔ 이건 SKILL.md 가 이미 경고하던 실패 모드다("stale 한 base 위로 리베이스하면 게이트가 전부
통과한다"). 자동 해석은 그 방어가 막으려던 상황을 **스스로 만든다.**

판별자를 **ref 존재 여부**로 바꿨다.

```bash
BASE="$(git config --get fz-rebase.base || true)"          # ① 프로젝트가 정한 값
if [ -z "$BASE" ]; then
  if git rev-parse --verify -q "${PRIMARY}/develop" >/dev/null; then
    BASE="${PRIMARY}/develop"                               # ② 실재하면 사용
  else
    BASE=""                                                 # ③ 사용자에게 확인
  fi
fi
```

⛔ remote HEAD 는 사다리의 폴백으로도 넣지 않는다. "친절한 폴백" 으로 재진입하면 같은 실패가
되살아난다. ③ 에서 `main`·`master`·`release/*` 는 배포 브랜치일 수 있다고 표시하되 **자동
배제는 하지 않는다** — 팀마다 브랜치 운용이 달라 이름 기반 판정은 또 다른 오판이다.

## 4. `--remerge-diff` 실패를 삼켜 L2 검출이 조용히 꺼진다

`snapshot` 과 `prepush` 가 `2>/dev/null` 로 stderr 를 버린다. 옵션 미지원으로 실패해도 출력이
0줄이고, **0줄은 "수동 해결이 없다" 와 구분되지 않는다.** 결과는 두 가지다.

- `audit` 에서 L2(머지 수동 해결 미재적용) 검출이 통째로 꺼진다
- `prepush` 에서 원격의 evil merge 가 HALT 대신 WARN 으로 격하된다

진입부에 probe 를 넣었다. ⛔ HALT 로 올리지 않는다 — 버킷 분할과 형태 게이트는 그대로 작동하므로
구버전 git 사용자의 나머지 방어까지 막을 이유가 없다. 꺼졌다는 사실만 알린다.
