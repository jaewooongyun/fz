# v4.42.0 (2026-09-28) — 리뷰는 확신 없는 후보를 발견 단계에서 지웠고, 같은 이슈를 세 번 옮겨 적었다 [MINOR]

> R-B 품질 축. 리뷰·계획의 품질을 올리는 길을 **옵션으로** 넣는다. 워크플로 옵션 셋과 `--render` 는 기본 off 라서, 주지 않으면 워크플로의 모든 콜 입력이 기준(v4.39.1)과 바이트 단위로 같다. 측정 없이 출하한다 — 옵션을 켠 효과는 R-C(v4.43.0)의 A/B 에서 한 번에 판정하고, 기본값 전환도 그 뒤다.

## 1. 무엇이 문제였나

- **발견 단계가 후보를 먼저 지웠다.** peer-review 의 공통 지시문과 이슈 스키마가 렌즈에게 "confidence 80 미만은 보고하지 않는다" 를 요구했고, 렌즈가 미리 올리는 스킬(arch-critic · code-auditor)과 Lead 절차 모듈에도 같은 문장이 있었다. 게시 여부를 판정하기도 전에 개선 제안이 생성 단계에서 사라졌다. 문장은 8곳이었고, 그중 Synthesize 계약 줄(`confidence<80 미보고`)은 표기가 달라 고정 문구 목록에 걸리지 않았다
- **Lead 가 같은 이슈를 세 번 옮겨 적었다.** peer-review 호출당 Bash 인자 p50 67,584자 가운데 review-report.md 가 18.1%, pr-comments.md 가 13.4% 였다. 줄 앵커와 게시 payload 도 인라인 python 으로 다시 짰다(인라인 python 298건 중 코멘트·줄·앵커·payload 주제 175건). 셋이 어긋나도 알 수단이 없었다
- **병합 규칙이 문서에만 있었다.** 렌즈와 GPT 발견의 dedup · 귀속 · 근거 확인 · 게시 등급을 Lead 가 판단과 섞어 손으로 했다
- **리뷰가 코드 품질 축을 축별로 남기지 않았다.** 관용 · 네이밍 · 아키텍처 규칙 · UI 구조 · 배치 · 설계 대안을 무엇으로 봤는지 기록이 없었고, 프로젝트 규칙의 출처와 범위를 확인하는 장치가 없어 없는 규칙을 추정 적용하거나 상충 규칙을 임의로 고르는 것을 막지 못했다
- **교차 스테이지가 필수 필드를 빠뜨려 스키마 재출력이 났다** — 18회 중 4회
- **fz-plan 의 델타 반영과 독립 플랜 대조가 손 작업이었다**

## 2. 무엇을 고쳤나

| 항목 | 켜는 법 | 켜면 |
|---|---|---|
| 후보 보존 (S16b) | `args.preserveLowConfidence` | 조기 필터 문장을 `[후보 보존]` 으로 |
| 단일 출처 렌더 (S20b) | `--render` | review.json 하나에서 세 산출물 |
| 결정론 병합 (S20) | `review_merge.py` 호출 | dedup · 보존 · 게시 등급 |
| craft 6축 (S16) | `args.craftAxes` | arch 렌즈 6축 + axisCoverage |
| 필수 필드 재고지 (S17) | `args.crossRequiredFields` | Stage 2 에 required 키 |
| 규칙 추출 · 검증 (S15) | fz-plan 절차 1.5 | 검증된 규칙 레코드만 |
| 델타 · 차이표 (S21) | 스크립트 호출 | Step 귀속 · 차이표 |

- **후보 보존** — 옵션을 켜면 공통 지시문의 조기 필터 문장과 이슈 스키마의 confidence 설명을 **사본에서만** `[후보 보존]` 문장으로 바꾼다. 원본 상수는 그대로라 꺼지면 여섯 콜이 기준과 같다. 그 설명은 스키마 네 곳이 참조로 공유해 콜마다 사본을 쓴다. 렌즈 스킬과 Lead 모듈의 원문은 두고 `[후보 보존]` 이 있을 때만 임계를 적용하지 않는다는 조건부 줄을 달았다
- **단일 출처 렌더** — Lead 는 판정과 문장만 `review.json` 에 쓰고 `render_review.py` 가 review-report.md · pr-comments.md · payload.json · render-preview.json 을 만든다. 줄 앵커는 `diff_anchors.py` 의 계산을 그대로 쓴다. 게시 계약(top-level body = 리포트 전문 · 다중 라인 `start_line`·`start_side`·`line`·`side` 넷 · 단일 줄 `line`·`side`)을 지키고, 겹치는 hunk 는 site 의 `pick` 이 없으면 거부하며, 확인 게이트 (a)(b)(c) 사유를 미리보기에 적는다. 세 산출물에 이슈 id 를 숨은 주석으로 달아 서로 대조하고 게시 뒤 착지 검증에서 짝을 맞춘다. 게시와 사용자 확인 절차는 그대로다
- **결정론 병합** — `review_merge.py` 가 §3 키(파일 · 줄 범위 겹침 · 축)로 묶되 후보를 지우지 않는다(입력 수 = 출력 수). 근거 인용을 diff hunk 에서 다시 찾아 없으면 hold 로 둔다(삭제 아님). 게시 등급은 pre-existing 을 suggestion 으로 cap 하고, 확신도 80 미만 결함은 hold, craft 는 ruleRef 가 있고 확신도 80 이상일 때만 post 로 매긴다. GPT reverse 는 question 으로 바꾸고, 오염 표시가 붙은 GPT 입력은 거부한다. 계약은 `modules/peer-review-gates.md` §10
- **craft 6축** — arch 렌즈에만 6축 줄과 축별 axisCoverage 스키마를 준다. 규칙 레코드가 없으면 "규칙 인용 지적 금지 — 코드 근거만" 이 붙는다
- **필수 필드 재고지** — Stage 2 교차 프롬프트에 additions 항목의 required 키를 적는다. 키 목록은 스키마에서 런타임에 읽는다
- **규칙 추출 · 검증** — 지침 원문 색인(`extract_project_rules.py`, 해석 없음) → 모델이 각자 쓴 규칙 레코드 → `check_project_rules.py --check` 통과본만 쓴다. ⚠️ 이것은 옵션이 아니라 **fz-plan 절차 1.5 의 Lead 절차 변경**이다. 워커에 넘기는 `archConstraints` 는 옛 형식(4축 + conflicts, 순서 포함)의 호환 투영이고, 넘기지 않으면 워커 프롬프트는 바뀌지 않는다(`arch-constraints-projection.js`)
- **델타 · 차이표** — `plan_apply_delta.py` 는 lean2 병합 콜의 수정 지시 · 경계 사례를 Step id 에 **붙인다**(본문 수정은 Lead 몫 · 모르는 id 거부 · 추가 영향은 출처를 달아 readScope 에만 · unresolved 보존 · 멱등). `plan_divergence.py` 는 한쪽에만 있는 변경 파일 · GPT 플랜이 구현 파일을 건드리지 않는 RTM 요구 · 글자 겹침으로 짝을 못 찾은 위험을 표로 만든다(두 입력 필수 · 오염 표시 거부 · GPT 입력은 JSON 만)

## 3. 하지 않은 것

- **측정** — 옵션을 켠 효과(SC-3 발견 손실 · SC-4 6축 · SC-6 시간 · SC-7 비용 이동)는 재지 않았다. R-C 의 A/B 에서 옵션을 켠 arm 으로 판정하고 기본값 전환은 그 판정 뒤다. 그때까지 조기 필터와 이중 작성은 기본 경로에 남는다
- **GPT 스킬 본문 정비** — 설치되는 스킬 본문을 바꾸므로 기본 off 옵션이 될 수 없어 R-C 로 옮겼다
- **배선** — fz-plan 이 `plan_apply_delta.py` · `plan_divergence.py` 를 부르는 절차와 GPT 독립 플랜 JSON 스키마는 R-C 다. Synthesize 가 `review_merge.py` 를 부르게 하는 절차도 이 판에 없다
- **위험 짝짓기** — 차이표의 위험 대조는 글자 겹침이라, 실제 두 독립 플랜에서 가장 비슷한 쌍도 유사도 0.13 이었다. 위험 표는 짝을 지어 주는 표가 아니라 나란히 보는 표다
- **열린 finding** — F-339(git 이 무시하는 로컬 폴더까지 훑는 표면 검사) · F-340(분할 커밋의 앞 커밋이 뒤 커밋 경로를 가리킴) · F-341(게이트 CHECK 와 스텝의 기본 off 가 모순) 은 닫지 않는다
