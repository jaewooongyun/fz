## 1. 무엇이 문제였나

- **병합 콜이 다시 조사했다(F-345).** plan-lean2 의 Stage 2 병합 콜은 델타 전용 스키마인데 도구 제한이 없었다. 렌즈가 이미 본 코드를 다시 읽고 검색해(한 run 실측 Read 28 · Grep 20) 크리티컬 패스 두 단 가운데 하나를 그 재조사가 차지했다
- **Lead 가 Workflow 를 늦게 띄웠다.** R-C 18 run 을 구간으로 나눠 보니 Workflow 구간은 arm 사이 거의 같았고, 차이와 잡음은 Lead 쪽이었다. 18 run 중 16 run 이 Workflow 를 띄우기 전에 자문을 먼저 불렀다
- **fz-review 렌더 단계가 렌더러 코드를 읽었다.** 렌더러 입력 형식을 알 방법이 코드뿐이었다
- **fz-plan 이 두 arm 모두 같은 채점 항목을 놓쳤다(F-352).** 놓친 항목의 원인을 나눠 보니 일부는 렌즈가 아예 묻지 않는 축이었다
- **GPT effort 가 config 에 닿지 않았다.** effort 가 래퍼 기본 high · 문서 리터럴 21곳 · 표 4벌로 흩어져, config 에 둔 effort 가 fz 의 GPT 호출에 쓰이지 않았다. 독립 첫 패스 런처도 자기 기본값(plan xhigh · review high)을 썼다

## 2. 무엇을 바꿨나

| 항목 | 이전 | 지금 |
|---|---|---|
| 병합 콜 | 도구 제한 없음 | `fz:plan-merge`(도구 없음) |
| Workflow 기동 | 자문 · 확인 뒤 | 입력 확정 즉시 |
| 렌더 입력 형식 | 렌더러 코드를 읽음 | `--example` 예시 |

- **병합 전용 에이전트** — `agents/plan-merge.md` 는 `tools:` 가 비어 있다. Workflow 런타임은 구조화 반환용 StructuredOutput 만 넣는다(프로브: 부여된 도구 = StructuredOutput 하나 · 읽기를 시켜도 도구 호출 0). 접을 근거가 입력에 없으면 unresolved 에 적는다. 기본값 회귀 검사는 이 변환만 의도된 기본 경로 변경으로 받는다
- **Workflow 먼저 기동** — fz-review · fz-plan 의 TEAM 실행 절차에서 Workflow 호출 단계 앞에 규칙을 두었다. 입력이 아닌 일(외부 자문 · 참조 무결성 확인 · L3 에이전트)은 Workflow 가 도는 동안 하고, 방향이 정해지지 않았을 때만 자문을 먼저 한다. GPT 독립 패스의 기동 순서(기동 < Workflow < 병합)는 그대로다
- **렌더러 입력 예시** — `python3 scripts/render_review.py --example`
- **fz-plan 렌즈 축** — edge 렌즈: 인증 상태별 진입 · 원격 차단 경로 · 되돌리기 범위. impact 렌즈: 계측 위치 · 구버전 공존 · 레이아웃 제약 파급
- **채점표 유출 검사** — `scripts/check_rubric_leakage.py` 가 품질 fixture 채점표 문장(공백 정규화)이 fz-plan 프롬프트 자산에 들어가지 않았음을 본다. 요약 · 바꿔 쓰기는 못 잡는다
- **기본값 검사** — `tests/workflows/default-arms.js` 가 원장 판정의 판정 불가(judge exit 2)를 off 로 읽지 않는다. 빈 원장에서도 기본값 대조가 통과하던 구멍이다
- **GPT 모델 · effort 세션 선택** — GPT 를 쓰는 세션은 초반에 한 번 묻는다(/fz 는 Phase 4 질문에 합치고, 개별 스킬은 첫 GPT 호출 직전). 래퍼가 필드마다 플래그 > 세션 선택 > config 순으로 정하고 호출 직전 `GPT-CHOICE` 한 줄로 적용값과 출처를 찍는다. 정본은 `modules/gpt-strategy.md` § 모델·effort 선택이고, 서브커맨드별 effort 표와 모델이 부를 수 없는 Plugin 우선 경로는 걷어냈다. peer-review Tier 1·2·3 challenger 와 fz-modernize Phase 4 가 래퍼 한 형태로 부르고, 독립 첫 패스 런처도 같은 규칙이다. 선택하지 않은 자율 · 헤드리스 세션은 config 그대로다

## 3. 측정 (R-D 확인 run · S36)

판정 규칙을 run 전에 등록하고, 판정 스크립트의 sha256 을 게이트가 고정했다. fz-plan 기본 경로를 품질 fixture 두 개에 1 run 씩 돌려 가린 판정으로 채점했다. ⛔ 잰 트리는 GPT 통로를 합치기 **전**(R-D W6 만)이다.

| fixture | ① 놓쳤던 항목 | ② 회귀 | 판정 |
|---|---|---|---|
| plan-feature | 0/3 | 0 | FAIL |
| plan-removal | 3/3 | 0 | PASS |

- ① 은 feature {B1 · Q5a · Q6a} · removal {B1 · Q3a · RF1} 가운데 2개 이상 충족이다. feature 셋은 R-C 4 run 에서도 0 이었고 이번에도 0 이다. removal 셋은 R-C 4 run 에서도 1~2회 충족된 항목이라, N=1 의 3/3 은 run 사이 변동과 구별되지 않는다
- ② 는 R-C 같은 fixture 4 run 이 모두 충족한 항목(feature 13 · removal 25)을 잃지 않는 것이다. 두 fixture 모두 빠짐 0 이다
- R-C 기준 run 을 같은 꾸러미에 대조로 넣어 다시 판정받았다. 검증자 세션은 관대하지 않았다(feature 판정 변화 0 · removal 은 한 항목 더 엄격)
- 병합 콜(판정에 쓰지 않는 기록): 두 run 모두 1턴 · 도구 1(StructuredOutput) · 탐색 0 이다. 같은 계측으로 R-C 8 run 은 도구 11~18 · 3~7턴이었다. wall 은 feature 326s · removal 288s 로 R-C 범위(409~629s · 289~415s)의 아래쪽이지만, N=1 이고 CLI · 계정이 달라 크기로 읽지 않는다
- 측정 중 생긴 일 두 가지를 판정 전에 기록하고 처리했다. 첫 시도는 사용량 한도로 멈춰 무효로 두고 다시 쟀다. 다시 잰 run 은 A/B 수집기의 탐지 공백 두 가지(스크립트가 argv 로 조립한 끝점 쓰기 · 호출 뒤 옮긴 GPT 로그) 때문에 미완주처럼 기록됐다. 수집기 사본으로 그 행만 다시 수집했고, 같은 사본으로 R-C 18 run 을 다시 수집해도 판정 필드가 바뀌지 않음을 확인했다

## 4. 하지 않은 것

- **GPT 통로의 대화형 경로는 실사용 확인 전이다.** 커밋마다 격리 clone 에서 health-check 와 선택 검사를 통과했고 통로 검사 73건이 통과했지만, 첫 GPT 호출 전 질문 · 세션 중 변경을 실제 대화로 확인하지 않았다. 이 판을 A/B arm 으로 쓰려면 기준선을 다시 동결한다(GPT effort 출처가 래퍼 기본에서 config 로 바뀌었다)
- **F-352 는 닫지 않았다.** 렌즈 축을 더해도 feature 쪽 세 항목이 잡히지 않았다. 같은 fixture 로 다시 고치고 재면 과적합이라, 다음 시도는 새 fixture 로 잰다
- **A/B 수집기의 탐지 공백(F-361)은 트리에 넣지 않았다.** 수집기를 바꾸면 계측기 지문이 바뀌어 R-C 채점 18행이 낡은 것이 된다. 다음 판에서 R-C 재채점과 함께 넣는다
- **F-345 의 남은 두 레버** — 렌즈의 code-context 재독과 출력 생성 지배는 이 판 범위 밖이다. F-362 로 이어 간다
- fz-review(review-live) · fz-plan(plan-lean2) 의 C 옵션은 기본 off 그대로다(opt-in)
