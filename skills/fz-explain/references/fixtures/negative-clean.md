# fixture — 게이트를 이미 만족하는 문서

> 용도: 게이트 G1~G8 의 **과잉 검출**을 재는 오라클(negative).
> 짝: `positive-defects.md` — 검출력을 재는 쪽.
>
> ⛔ positive 만 있으면 검출력만 재고 과잉은 못 잰다. 게이트가 정상 문서를 결함으로 오판하면
> 스킬이 쓸모없어진다. **기대 검출 0건.**

## 이 기능은 어떻게 동작하나  (층 0~2)

사용자가 목록에서 항목을 고르면 상세 화면이 열린다. 그 사이에 세 단계가 있다.

1. 사용자가 항목을 탭한다
   → `Sample/ListView.ext:45` `onItemTap`
2. 화면이 자기 라우터에게 이동을 요청한다
   → `Sample/ListRouter.ext:88` `routeToDetail`
3. 라우터가 빌더로 상세 화면을 만들어 붙인다
   → `Sample/DetailBuilder.ext:20` `build`

한 줄 정리: 목록 화면이 자기 라우터를 통해 상세 화면을 직접 만들어 띄운다.

## 등장하는 것  (층 1)

```
DetailBuilder [A]
선언:          `func build(listener:) -> DetailRouting` — Sample/DetailBuilder.ext:20
하는 일:        상세 화면의 구성요소를 만들어 하나로 묶어 돌려준다
왜 지금 나오나:  3단계에서 라우터가 이것을 호출한다

Builder [B]
역할:          화면 하나를 이루는 조각들을 조립해 완성품으로 내주는 자리
이 프로젝트에서: 화면마다 하나씩 있고, 부모 라우터가 자식을 만들 때 호출한다

ListView [A]
선언:          `final class ListView: BaseView` — Sample/ListView.ext:12
하는 일:        항목 목록을 그리고 탭을 상위로 알린다
왜 지금 나오나:  1단계에서 사용자 입력이 여기로 들어온다

하는 일:        목록 화면의 자식 붙이기·떼기를 맡는다

하는 일:        상세 화면의 처리 결과를 상위로 통지한다

왜 지금 나오나:  구조 근거에서 주입 지점으로 등장한다
```

한 줄 정리: `DetailBuilder` 는 상세 화면 조립을 맡고, `Builder` 는 그 역할의 일반 이름이다.

## 동작↔코드 1:1 매핑  (층 2)

### 동작: 항목을 탭하면 상세 화면이 열린다

**담당 코드**: `Sample/ListRouter.ext:88` — `routeToDetail`
**하는 일**: 빌더로 상세 화면을 만들고 자식으로 붙인 뒤 화면 스택에 올린다
**없으면**: [기계적] 탭 핸들러가 호출할 대상이 없어 컴파일이 실패한다
**왜 여기인가**: [실측: 채택자 3] 화면을 붙이고 떼는 책임이 라우터에 모여 있다
**상태**: 기존 구조

### 동작: 뒤로 나가면 상세 화면이 정리된다

**담당 코드**: `Sample/ListRouter.ext:104` — `detachDetail`
**하는 일**: 붙여 둔 자식을 떼고 화면 스택에서 내린다
**없으면**: [기계적] 자식 참조가 남아 화면이 해제되지 않는다
**왜 여기인가**: [실측: 호출자 2] 붙인 쪽이 떼는 것이 이 계층의 규칙이다
**상태**: 기존 구조

### 동작: 상세 화면이 목록에 결과를 돌려준다

**담당 코드**: `Sample/DetailInteractor.ext:66` — `notifyResult`
**하는 일**: 처리 결과를 상위 listener 로 올린다
**없으면**: [추론] 목록이 갱신 시점을 알지 못해 화면이 낡은 상태로 남을 것으로 보인다
**왜 여기인가**: [문서: 아키텍처 규칙 상향 통지] 아래에서 위로만 알린다
**상태**: 기존 구조

한 줄 정리: 이동·정리·통지 셋이 각각 한 함수에 대응하고, 붙인 쪽이 떼는 규칙이 그 배치를 정한다.

## 왜 이 구조인가  (층 3)

### `DetailBuilding` 이 프로토콜인 이유
채택자: `DetailBuilder`, `StubDetailBuilder`, `PreviewDetailBuilder` [실측: 채택자 3]
주입 지점: `Sample/ListComponent.ext:31`
구체 타입을 직접 쓰지 않는 대신 테스트에서 가짜 구현을 넣을 수 있다.
새 구현을 넣으려면 프로토콜을 채택하고 컴포넌트에서 바꿔 끼우면 된다.

### 만약 주입 대신 직접 생성했다면
[기계적] 목록 화면 테스트가 상세 화면 전체를 함께 만들게 되어, 상세 쪽 변경이
목록 테스트를 깨뜨린다.

한 줄 정리: 프로토콜은 테스트 대역을 끼우기 위한 자리이고, 채택자가 셋이라는 사실이 그 근거다.
